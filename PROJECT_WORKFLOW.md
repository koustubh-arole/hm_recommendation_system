### `pipelines/data_prep_pipeline.py` — Data Cleaning

**What it does:**
- Reads all 3 raw CSVs
- Chunks `transactions_train.csv` in 500,000-row batches to avoid OOM on 3.3 GB file
- Filters transactions from `TRANSACTIONS_START_DATE = "2019-09-22"` onwards
- Cleans nulls in customers.csv: `age` → median fill, `fashion_news_frequency` → `"NONE"`
- Builds `article_lookup.csv` with deduplicated product metadata
- Writes `transactions_small.csv` (filtered subset for faster downstream processing)

**Key constants:**
```python
TRANSACTIONS_START_DATE = "2019-09-22"   # Only recent data for relevance
CHUNK_SIZE = 500_000                      # Memory limit for 3.3 GB file
```

**KEY THINGS TO REMEMBER:**
- If you re-run without `--skip-data-prep`, the whole 3.3 GB file gets reprocessed
- `transactions_small.csv` is the source of truth for ALL downstream pipelines

---

### `pipelines/rfm_pipeline.py` — Customer Segmentation

**What it does:**
1. Groups transactions by `customer_id` to compute:
   - **Recency** = days since last purchase (lower = better)
   - **Frequency** = total number of transactions
   - **Monetary** = total spend (raw H&M units × `SCALING_FACTOR`)
2. Applies `StandardScaler` to normalize all three metrics
3. Runs `KMeans(n_clusters=5, random_state=42, n_init=10)` on scaled RFM
4. Assigns each of 1,362,281 customers to a cluster 0–4
5. Writes `rfm_segmented.csv`

**The 5 Clusters (derived from centroid analysis):**

| Cluster | Label | Recency | Frequency | Monetary | Size |
|---------|-------|---------|-----------|----------|------|
| 3 | Champions | ~45 days | ~136 txn | High | ~15% |
| 4 | Loyal Customers | ~79 days | ~47 txn | Medium | ~20% |
| 0 | Potential Loyalists | ~128 days | ~16 txn | Low | ~25% |
| 2 | At-Risk Customers | ~172 days | ~3 txn | Low | ~22% |
| 1 | Lost Customers | ~565 days | ~5 txn | Low | ~18% |

**Key constants:**
```python
N_CLUSTERS = 5
random_state = 42
n_init = 10
```

**KEY THINGS TO REMEMBER:**
- KMeans cluster numbers (0–4) are assigned randomly by the algorithm — the labels (Champions, etc.) were derived by looking at the actual centroid values AFTER training
- `random_state=42` ensures reproducible cluster assignments across runs
- Both `engine.py` and `api/main.py` use the same cluster label mapping

### `pipelines/recommendation_pipeline.py` — Recs Generation

**What it does (3 types of recommendations):**

```
Type 1: Cluster Recommendations
────────────────────────────────
For each cluster (0-4):
  Count purchase frequency of each article among cluster members
  → Top-10 articles per cluster
  → Writes cluster_recommendations.csv

Type 2: Co-Purchase Recommendations
─────────────────────────────────────
Self-join transactions on (customer_id, t_dat):
  "customers who bought A also bought B on the same day"
  → Count (A, B) pairs across all customers
  → Keep top-5 recs per article (CO_TOP_RECS = 5)
  → Writes co_purchase_recs.csv

Type 3: User-Level Recommendations
────────────────────────────────────
For each customer with ≥1 transaction:
  1. Get their cluster's top-10 products
  2. Remove products they've already bought
  3. Add remaining cluster products ranked by score
  → Writes user_recommendations.csv (1 row per customer-article pair)
```

**Key constants:**
```python
TOP_N = 10          # Recs per user
CO_TOP_ITEMS = 50   # Max unique items in co-purchase analysis
CO_TOP_RECS = 5     # Co-purchase recs per article
```

### `pipelines/price_pipeline.py` — Price Conversion

**What it does:**
- Reads raw transaction prices (H&M internal scaled units)
- Divides by `USD_DESCALE = 590` to get USD equivalent
- Multiplies by `USD_TO_INR = 83.5` to get Indian Rupees
- Clips to `MIN_PRICE = 99`, `MAX_PRICE = 24999` (realistic retail range)
- Writes `article_prices.csv` with final INR prices

**KEY THINGS TO REMEMBER:**
- The `590` scaling factor was reverse-engineered from the dataset (prices in raw CSV are ~590× actual USD value)
- Without this pipeline, all prices show as `null` in the frontend
- `engine.py` also has `SCALING_FACTOR = 590` for the same reason

---

### `pipelines/forecasting_pipeline.py` — Demand Forecasting

**What it does:**
1. Creates lag features from historical sales (7-day, 14-day, 28-day lags)
2. Adds date features: `day_of_week`, `month`, `week_of_year`, `is_weekend`
3. Trains `XGBRegressor` on historical daily demand per article
4. Predicts demand for the next 30 days
5. Writes `forecast_output.csv` (article × date × predicted_demand)
6. Writes `forecast_summary.csv` (total, daily_avg per article)

**KEY THINGS TO REMEMBER:**
- Only articles with sufficient history (≥30 days of sales data) are forecasted
- Model file saved as `models/xgb_demand_model.pkl`
- The forecasting endpoint (`/api/admin/forecast`) reads both output files

---

### `pipelines/trending_pipeline.py` — Trending Products

**What it does:**
- Counts purchase frequency in the last 7 and 30 days from `transactions_small.csv`
- Keeps top-50 articles by purchase count for each window
- Writes `top_products_7d.csv` and `top_products_30d.csv`

### `pipelines/full_retraining_pipeline.py` — Orchestrator

```python
def run_pipeline():
    _run_stage("Data Prep",      data_prep_pipeline.run_pipeline)   # Stage 1
    _run_stage("RFM",            rfm_pipeline.run_pipeline)          # Stage 2
    _run_stage("Recommendations", recommendation_pipeline.run_pipeline) # Stage 3
```

**KEY THINGS TO REMEMBER:**
- Use `--skip-data-prep` flag to skip stage 1 if raw data hasn't changed
- Each stage is wrapped in try/except — a failed stage prints an error but doesn't crash the whole pipeline
- Can be triggered from the UI via `POST /api/admin/retrain` which runs it in a daemon thread

### `api/auth.py` — Authentication

**Database:** SQLite at `data/users.db`

```
users table:
  id INTEGER PRIMARY KEY AUTOINCREMENT
  username TEXT UNIQUE NOT NULL
  email    TEXT UNIQUE NOT NULL
  password TEXT NOT NULL              ← SHA256 hex hash (no salt!)
  role     TEXT DEFAULT 'user'        ← "admin" or "user"
  customer_id TEXT                    ← links DB user to H&M customer data
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
```

**Password hashing:**
```python
def _hash_password(p: str) -> str:
    return hashlib.sha256(p.encode()).hexdigest()  # SHA256, no bcrypt
```

**JWT creation:**
```python
SECRET_KEY = os.getenv("JWT_SECRET", "CHANGE_ME_IN_PRODUCTION_use_openssl_rand")
ALGORITHM = "HS256"
ACCESS_TOKEN_EXPIRE_MINUTES = 60 * 8   # 8-hour sessions

# Normal login JWT payload:
{"sub": "admin", "role": "admin", "exp": ...}

# Customer-ID login JWT payload:
{"sub": "00006413d8573cd2", "role": "user",
 "customer_id": "00006413...full64chars...", "cluster": 3, "exp": ...}
```

**Two login routes:**

```
POST /auth/login
────────────────
Input:  {username, password}
1. Look up user in SQLite by username
2. SHA256 hash the input password
3. hmac.compare_digest() against stored hash
4. If match → create JWT with {sub, role}
5. Return: {access_token, role, username, customer_id}

POST /auth/login/customer
─────────────────────────
Input:  {username: "<customer_id>", password: ""}
1. Load rfm_segmented.csv (no DB lookup needed)
2. Find row where customer_id matches (tries exact, then lstrip("0"))
3. Read cluster from that row
4. Create JWT with {sub: first16chars, role: "user", customer_id: full_id, cluster}
5. Return: {access_token, role: "user", username: "Customer XXX...", customer_id}
```

**Authorization middleware:**
```python
def get_current_user(credentials) -> dict:
    # Decodes JWT
    # If JWT has customer_id → virtual customer (no DB row needed)
    # Else → look up real user in SQLite

def require_admin(current_user) -> dict:
    # Raises 403 if role != "admin"
    # Used as: _admin=Depends(require_admin)
```

**KEY THINGS TO REMEMBER:**
1. Default admin is seeded on first run: `admin / admin123`
2. SHA256 passwords are NOT salted — fine for demo, not for production
3. Customer-ID login does NOT create a DB user — the JWT itself is the identity
4. `SECRET_KEY` defaults to a hardcoded string — must set `JWT_SECRET` env var in production
5. `lstrip("0")` is applied to customer_id in BOTH the login route and all data lookups

### `frontend/services/api.ts` — HTTP Client

**Setup:**
```typescript
const api = axios.create({
  baseURL: process.env.NEXT_PUBLIC_API_URL || "http://localhost:8000",
  timeout: 45000,

```

**Request interceptor:** Reads `localStorage.getItem("hm_token")` and adds `Authorization: Bearer <token>` header to every request.

**Response interceptor (401 handling):**
```typescript
if (err.response?.status === 401) {
  // CRITICAL: Only redirect if NOT already on /login
  // Without this guard, wrong password → 401 → page reload → error never shows
  if (typeof window !== "undefined" && window.location.pathname !== "/login") {
    localStorage.removeItem("hm_token");
    window.location.href = "/login";
  }
  return Promise.reject(err);  // ← Still reject so login page can show error
}
```

**Retry logic:** 500+ errors retry up to 2 times with 800ms delay.

**API namespaces:**
```typescript
authAPI   → /auth/*   (login, me, register, listUsers, deleteUser)
recsAPI   → /api/recommendations, /api/trending, /api/search, /api/customer/*/profile
adminAPI  → /api/admin/* (clusterStats, clusterRecs, coPurchase, retrain, forecast, health)
productsAPI → /api/products
```

**KEY THINGS TO REMEMBER:**
- The `window.location.pathname !== "/login"` guard in the 401 interceptor is critical for login to work
- All recs/products responses pass through `normaliseProduct()` before being stored in state
- `safe()` wrapper on some calls returns `null` instead of throwing (used for optional admin data)

### `frontend/store/authStore.ts` — Zustand Auth State

```typescript
State: { user, token, isAuthenticated, isLoading }

login(username, password):
  → calls authAPI.login()
  → stores token in localStorage("hm_token")
  → sets user + isAuthenticated = true

logout():
  → removes "hm_token" from localStorage
  → clears all state

checkAuth():    ← called on every page load
  → reads "hm_token" from localStorage
  → if JWT has customer_id field → it's a customer login, restore state from JWT payload directly
  → else → call GET /auth/me to verify with server
  → if /me fails → logout()
```

**Persistence:** Uses Zustand `persist` middleware with key `"hm-auth"` — stores user, token, isAuthenticated in `localStorage`.

**KEY THINGS TO REMEMBER:**
1. `checkAuth()` is called in `DashboardShell` on mount — it's the rehydration guard
2. Customer-ID logins skip the `/me` API call (the JWT contains all needed info)
3. The `persist` middleware and the manual `localStorage.setItem("hm_token")` both exist — they serve different purposes: persist handles the Zustand state snapshot, hm_token is the raw token read by the Axios interceptor

### `frontend/lib/normaliseProduct.ts` — Response Normalizer

**Problem it solves:** Different API endpoints return products with inconsistent field names:
- Recommendations: `prod_name`
- ChromaDB search: `metadata.product_name`, `document`
- Products endpoint: `product_name`
- Cluster recs: `prod_name`

**Solution:**
```typescript
export function normaliseProduct(raw: Record<string, unknown>): Product {
  return {
    article_id:  String(raw.article_id || raw.id || raw.articleId || "").replace(/^0+/, ""),
    product_name: String(
      raw.product_name || raw.prod_name || raw.name ||
      raw.metadata?.product_name || raw.document || "Unknown product"
    ),
    // ... similar fallback chains for all fields
    price: raw.price != null ? Number(raw.price) : undefined,
    score: raw.score != null ? Number(raw.score) : undefined,
  };
}
```

**KEY THINGS TO REMEMBER:**
- Every product that enters the frontend state goes through this function
- The `replace(/^0+/, "")` strips leading zeros from article_id on the frontend side too
- `score` is only present on personalised recs (0.0–1.0, shown as "% match")

## 9. End-to-End Request Flows

### Flow 1: Admin Login

```
1. User clicks "Admin Portal" button on /login
   → fillDemo("admin") fills: username="admin", password="admin123"

2. User clicks "Sign in →"
   → handleSubmit() calls login("admin", "admin123")
   → authAPI.login() → POST /auth/login {username, password}

3. FastAPI auth.py:
   → db_get_user("admin") → finds row in SQLite
   → _verify_password("admin123", stored_hash) → True
   → create_access_token({sub: "admin", role: "admin"})
   → returns {access_token, role: "admin", username: "admin", customer_id: null}

4. Frontend:
   → localStorage.setItem("hm_token", token)
   → Zustand: user={role:"admin"}, isAuthenticated=true
   → router.push("/overview")

5. /overview mounts → DashboardShell.checkAuth() runs → verifies token via /auth/me
   → Page renders with admin nav
```

### Flow 2: Customer ID Login

```
1. User switches to "Customer ID" tab
   → Clicks demo ID link → customerId state is set

2. User clicks "Load My Profile →"
   → handleCustomerLogin() → POST /auth/login/customer {username: customerID}

3. FastAPI auth.py:
   → Reads rfm_segmented.csv (from cache after first call)
   → Finds row: df[df["customer_id"] == customerID]
   → Gets cluster number from that row
   → create_access_token({sub: first16chars, role:"user", customer_id: fullID, cluster: 3})
   → returns token

4. Frontend:
   → Manually writes both localStorage("hm_token") AND Zustand state
   → Also writes hm-auth persist key directly (prevents stale persist state)
   → router.push("/home")

5. /home → fetches trending + recsAPI.forCustomer(customer_id) → displays picks
```

### Flow 3: Personalised Recommendations

```
1. /recommendations page mounts
   → useEffect fires when user.customer_id changes
   → recsAPI.forCustomer(cid) → GET /api/recommendations/{cid}
      Header: Authorization: Bearer <token>

2. FastAPI main.py:
   → get_current_user() → verifies JWT → extracts customer_id
   → Permission check: JWT customer_id.lstrip("0") must match URL parameter.lstrip("0")
   → get_cached_df("user_recommendations.csv") → in-memory DataFrame
   → Filter rows where customer_id matches (after lstrip)
   → Merge with articles.csv for product metadata
   → Merge with article_prices.csv for INR prices
   → Return top 40 results

3. Frontend:
   → normaliseProduct() called on each result
   → setRecs(r.recommendations)
   → ProductCard components render with image (picsum.photos seed)
```

### Flow 4: Pipeline Retrain (Admin)

```
1. Admin clicks "▶ Run" on Full Retraining card in /pipelines
   → run(pipeline) → POST /api/admin/retrain?pipeline=full

2. FastAPI:
   → require_admin() check passes
   → threading.Thread(target=full_retraining_pipeline.run_pipeline, daemon=True).start()
   → Returns immediately: {"detail": "Pipeline 'full' triggered.", "status": "running"}

3. Background thread runs:
   → Stage 1: data_prep_pipeline (5-10 min)
   → Stage 2: rfm_pipeline (2-4 min)
   → Stage 3: recommendation_pipeline (6-8 min)
   → Writes new CSVs to data/processed/

4. NOTE: _cache in main.py is NOT cleared automatically
   → Must restart FastAPI server for new CSV data to take effect
```

## 11. Common Errors & Their Fixes

### "Login shows failed / error not displaying"
**Root cause:** Axios 401 interceptor was firing `window.location.href = "/login"` for ALL 401 responses, including wrong-password on the login endpoint itself — causing a page reload before the error state could render.  
**Fix:** Added `window.location.pathname !== "/login"` guard in `services/api.ts`.

### "Customer ID not found"
**Root cause:** Leading zero mismatch between the ID as typed and the stored ID.  
**Fix:** `auth.py login_as_customer()` tries exact match first, then `.lstrip("0")` match.

### "No recommendations"
**Root cause 1:** `user_recommendations.csv` hasn't been generated — run `recommendation_pipeline.py`.  
**Root cause 2:** The customer_id in the URL doesn't match after `lstrip("0")` comparison.  
**Fallback:** API returns trending products (`top_products_7d.csv`) when user has no recs.

### "All prices showing null"
**Root cause:** `article_prices.csv` doesn't exist — run `price_pipeline.py`.

### "Search returns no results"
**Root cause:** ChromaDB isn't set up — run `utils/chroma_setup.py` once.  
**Verify:** Check `chroma_db/` directory exists and has files.

### "Fresh CSV data not appearing after pipeline run"
**Root cause:** `_cache` in `main.py` holds old DataFrames in memory.  
**Fix:** Restart the FastAPI server (`uvicorn api.main:app --reload`).

### "Admin can't access /overview"
**Root cause:** JWT role is not `"admin"` — either wrong login or old token.  
**Fix:** Clear localStorage, log in fresh with `admin / admin123`.

### "Pipeline runs in UI but data doesn't update"
**Root cause:** `daemon=True` thread — the pipeline runs but cache isn't refreshed.  
**Fix:** After pipeline completes, restart FastAPI server.
